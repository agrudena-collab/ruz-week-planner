# Расписание МеждОт25-2 — инструкции для Claude Code

## Цель проекта
Веб-приложение расписания студентов Финансового университета. Сейчас приложение работает для группы `МеждОт25-2`; следующая крупная цель — перейти к нескольким/всем группам, личным кабинетам и подпискам без потери текущей функциональности.

## Текущая архитектура
- `index.html` — основной frontend: расписание, поиск, фильтр, навигация по датам, ближайшая/текущая пара, архив, экзамены и UI изменений.
- `schedule.json` — актуальный снимок расписания.
- `schedule_previous.json` — временный предыдущий снимок, создаётся GitHub Actions перед обновлением.
- `changes.json` — результат сравнения предыдущего и текущего расписания.
- `changes_detector.py` — сравнивает расписания и определяет добавления, удаления и изменения.
- `ruz_client.py` — получает расписание из РУЗ ФУ.
- `planner.py` — дополнительная обработка расписания.
- `archive.json` — архив прошедших занятий.
- `exams.json` — данные экзаменов/зачётов.
- `sw.js` — Service Worker; для `schedule.json` и `changes.json` используется network-first с fallback на cache.
- `.github/workflows/main.yml` — обновление расписания, планировщик, детектор изменений и сохранение файлов.
- `.github/workflows/archive.yml` — архивирование прошедших занятий.

## Важные текущие функции
Не переписывать их без необходимости:
- ближайшая и текущая пара с countdown;
- сегодня / завтра / неделя / период;
- поиск и фильтр;
- статус занятия: сейчас / предстоит / завершено;
- архив;
- экзамены и зачёты;
- изменения расписания;
- ручное и автоматическое обновление;
- мобильная адаптация/PWA.

## Система изменений
`changes_detector.py` использует стабильный идентификатор слота:
`date + lessonNumberStart + lessonNumberEnd + group + subGroup + stream`.

Сравниваемые поля:
- `beginLesson`
- `endLesson`
- `discipline`
- `lecturer`
- `auditorium`
- `building`
- `kindOfWork`

Не считать исчезновение/появление записи на границе rolling-window реальным изменением.

ВАЖНО: `changes.json` — журнал обнаруженных изменений, а `schedule.json` — источник актуального расписания. Если РУЗ реально изменил пару, новая версия уже должна попасть в `schedule.json`; UI не должен пытаться подменять расписание данными из `changes.json`.

## Тестирование
Перед изменениями:
1. Изучить существующий код и связанные workflow.
2. Не дублировать уже существующую функцию.
3. Проверить влияние изменения на mobile/PWA и Service Worker.

После изменений:
1. Проверить JSON-синтаксис всех затронутых JSON-файлов.
2. Проверить Python-файлы на синтаксические ошибки.
3. Проверить GitHub Actions YAML.
4. Проверить, что frontend не ломает существующие views.
5. Если меняется `changes.json`/`schedule.json`, проверить cache/network поведение.

## Правила разработки
- Не переписывать `index.html` целиком ради маленькой функции.
- Не удалять существующие функции без явного требования.
- Не добавлять библиотеки без необходимости.
- Не хранить секреты, токены или платёжные ключи в репозитории.
- Не делать вид, что backend существует: сейчас проект в основном статический + GitHub Actions.
- Перед переходом к аккаунтам/подпискам сначала спроектировать backend/API и БД.
- Для multi-group архитектуры не создавать отдельный статический frontend-файл на каждую группу.
- При больших изменениях сначала составить план, затем менять код небольшими проверяемыми шагами.

## Ближайший roadmap
1. Надёжно довести систему изменений и автоматического обновления расписания.
2. Поддержка всех учебных групп РУЗ.
3. Backend/API + БД.
4. Регистрация, авторизация и личный кабинет.
5. Уведомления.
6. Подписки и платежи.
7. Production hardening, безопасность, мониторинг и резервное восстановление.

## Стиль UI
Сохранять существующий тёмный минималистичный стиль. Предпочтение: чистый интерфейс, крупная типографика, карточки, аккуратные акценты, мобильная адаптация. Не добавлять визуальный шум.
